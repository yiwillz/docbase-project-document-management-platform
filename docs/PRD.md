# 项目文件管理平台 第一版 PRD

> 定稿日期：2026-10-22；2026-10-23 增加第 11 节"产品化要求"；2026-10-23 调整：项目结构改为在平台内设置，不做客户 MDL 自动导入（F2、P1）。以本文件为准（早先的在线版未包含第 11 节）。
> 技术方案已选定方案 A（Python 轻量单体），见第 8–9 节。
> 产品定位：先在试点项目使用，最终作为私有化部署产品卖给其他总包企业，见第 11 节。

第一版做项目文件管理基座：文件自动命名归档、按 MDL 追踪应交文件、一键交付。AI（第二版）和审批流程（第三版）不在本版范围，但数据模型和接口为它们预留了位置。

## 1. 概述

第一版要让一个总包项目的所有文件"有编号、放对位置、知道缺什么、一键交付"，并替代手工维护的 MDL。

**第一版做**

- 项目结构（里程碑、文件种类、模块）在平台内设置，编号自动生成，提供从 Excel 粘贴、批量操作、复制已有项目；设备从设备清单 Excel 导入；所有变更留历史。
- 两种存文件方式：放到对应位置；描述一下让系统自动定位（规则识别）。
- 自动命名、自动升版、只保留最新 3 版（客户文件全部保留）。
- 应交矩阵：缺件、状态、逾期、完成率，并自动生成可编辑的 MDL Excel。
- 浏览检索、交付打包、共享盘只读镜像、阶段基线。
- 存量 80 GB 文件批量导入与清理。
- 登录、三档权限、操作审计。

**第一版不做**

- AI 识别、AI 预审、知识库问答（第二版）。
- 审批流程、发文、推送 Procore / Jira、预警通知、供应商门户（第三版）。
- 在线编辑 Office / CAD；ERP / PLM 集成。

**成功标准**

| 指标 | 目标 |
| --- | --- |
| 存量文件自动正确归档率 | ≥ 90%，其余进入待归类 |
| 小于 150 MB 的新文件从上传到归档 | ≤ 1 分钟 |
| 交付打包 | 从半天人工整理降到一键导出 |
| MDL 维护 | 不再手工编写，由平台生成 |

**设计原则**

1. 尽量不让人录入：项目结构只建一次（可粘贴、可复制已有项目），设备清单导入一次，之后存文件只需拖入和确认；上传没有必填表单。（Jira、Procore 的教训：设计好，但臃肿、录入多。）
2. 结构即数据：编号、位置、版本、状态都是结构化数据，不靠文件名解析来维持，第二版 AI 直接复用。
3. 每一步都可追溯、可撤销：变更留历史，批量操作先预演再执行。

## 2. 用户与权限

只在企业内网使用，同时在线 10–20 人，权限三档，按"项目成员"授权。

| 权限 | 典型人员 | 能做什么 |
| --- | --- | --- |
| 管理员 | 文控、IT | 全部；建项目、设置项目结构、导入设备清单、改配置、管用户、清空回收区 |
| 普通用户 | 项目经理、工程师、售前、售后 | 在所属项目内存文件、升版、归类、改状态、导出 |
| 只读用户 | 制造、装配调试等 | 在所属项目内查看、下载 |

权限模型预留"按文件种类限制可见范围"（如合同、报价只对项目经理可见）和"供应商只看自己的文件"两类规则，第一版不启用。

## 3. 核心概念与数据模型

项目结构（即 MDL：里程碑 → 文件种类）定义"应该交什么"，设备清单定义"交给哪台设备"，两者交叉得到应交项；文件填进应交项，版本挂在文件下。

| 概念 | 说明 | 来源 |
| --- | --- | --- |
| 项目 | 项目编号 + 名称；编号不进文件名，只用作导出包最外层文件夹 | 手建 |
| 里程碑（阶段） | MDL 的 Milestone，如 M3；带编号、名称、目标、截止日期；编号进文件编号 | 平台内设置 |
| 文件种类 | MDL 的一行：Submittal #（如 3.5，按文本存）、名称、分类、合同依据、是否按设备、是否按模块、截止日期、应含内容 / 说明 / 目的；另有"知识形态"字段留给第二版 | 平台内设置 |
| 模块 | 文件种类的分区；可指定对应哪些设备种类 | 平台内设置 |
| 设备种类 | 交付时的一级文件夹 | 设备清单导入 |
| 设备 | 设备编号（如 72，项目内唯一、不复用）、设备名、供应商、台数、别名；清单里的其他列原样存为属性；每台可记出厂编号 | 设备清单导入 |
| 应交项 | 一个"应该有的文件"的占位：按设备的种类每台设备一个，按模块的种类每个模块一个，其余每个里程碑下一个；带状态、责任方、截止日期 | 系统生成 |
| 文件 | 挂在应交项上的一个逻辑文件；不对应设备的应交项下可有多个文件，用标题区分；记录来源（客户 / 供应商 / 我方） | 存文件时生成 |
| 版本 | 文件的每次上传：V1、V2…、文件名、原始名、文件更新日、哈希、上传人；只增不改 | 存文件时生成 |
| 文件实体 | 磁盘上的真实文件，按哈希存，同内容只存一份 | 系统 |
| 阶段基线 | 某一时刻所有文件当前版本的快照 | 手动冻结 |
| 变更记录 | 谁、何时、改了什么（前 → 后）、原因；只增不改 | 系统 |
| 事件 | "新版本入库""状态变更"等事件的队列，第一版用于镜像同步，第二三版用于解析和推送 | 系统 |

关系：项目 → 里程碑 → 文件种类（可按模块分区）→ 应交项（× 设备 / × 模块 / 整个种类）→ 文件 → 版本 → 文件实体；设备种类 → 设备 → 应交项；阶段基线引用版本；版本入库和状态变更产生事件。

## 4. 功能需求

### F1 项目

1. 新建项目：编号（唯一）、名称、描述；可从已有项目复制里程碑、文件种类、模块、设备种类配置。
2. 项目列表显示完成率、缺件数、逾期数、待归类数；项目可归档为只读。
3. 项目成员管理：加人、设权限。

### F2 项目结构（里程碑、文件种类、模块）与 MDL

1. 项目结构在平台内设置，顺序为：建项目 → 建里程碑 → 在里程碑下建文件种类 → 在文件种类里可选设置模块分区、勾选对应的设备。里程碑（名称、目标、截止日期）、文件种类（名称、分类、合同依据、是否按设备、按哪些模块分区、对应哪些设备、截止日期、应含内容 / 说明 / 目的）、模块（项目内共用，可在设置分区时直接新建）。平台是 MDL 的唯一来源，MDL Excel 由平台按统一格式导出（F7.5），不再手工维护。
2. 编号：编号全部自动生成：里程碑 M1、M2…，文件种类"里程碑编号.序号"（3.9 之后是 3.10），不能手填；可插到指定位置，后面的往后挪；删除后后面的往前补；编号变动牵连到已挂文件的种类时不再自动变动（插入 / 调整顺序被拒绝，删除留空号）；停用不改编号；编号按文本存（4.1 与 4.10 不同）。
3. 少录入：表格式编辑；可从 Excel 复制多行粘贴；可批量设置模块分区；对应的设备可批量勾选（全部、按设备种类、按模块、逐台）；新项目可从已有项目复制整个结构（F1.1）。
4. 没用过的可以删除（变更记录里保留删除前的完整内容）；用过的（挂了文件、进过传送单或阶段基线）只能停用；全部留历史。（2026-10-27 第 17F 步统一为"没用过就能删，用过的才只能停用"，模块、设备、设备种类同样适用）
5. 模块可指定对应哪些设备种类，也可不对应。
6. 不做客户 MDL Excel 的自动解析导入：各家格式差异大、手工表格不规整，通用解析不可靠。客户更新 MDL 时在平台内对照修改。试点项目的结构也由用户在平台内建立（可用标准模板）。第二版由 AI 读取客户 MDL、产出平台标准模板格式的结构，人工预览确认后导入（见第 6 节）。
7. 结构随项目变化、MDL 有版本：客户的 MDL 是合同签订时的起点，项目中客户会随时追加或变更要交的文件。平台的项目结构是主数据，可随时调整；客户 MDL 是从平台结构导出、发给客户看的某个版本。
   - 每个文件种类有**要求类别**：合同规定 / 客户要求 / 内部要求；并记录**要求日期**、**依据**（合同条款、客户函件号等），要求内容后来变更时记录**变更日期**和**变更依据**。日期一律填业务上的真实日期，不知道就空着，不用录入日期冒充。
   - **合同外的客户新增要求**（要求类别为客户要求）：依据填客户提出要求的函件、邮件、会议纪要编号（没有合同依据，但有"客户要求过"的凭证）；记录**接受情况**（待确认 / 接受 / 不接受，新建时为待确认）及依据，不接受的应交项自动为不适用、仍留在客户 MDL 里显示"不接受：依据"；可记**变更单号**（VO / CO）。可导出合同外新增要求清单（提出日期、依据、接受情况、变更单号、完成情况）；汇总按要求类别分别统计完成率。
   - 给客户的 MDL 只放该给客户看的：**内部要求一律不出现**；合同规定、客户要求默认都列入（尽量给全），个别不想给的可以手动隐藏。
   - **MDL 版本**：MDL 本身也是要交给客户的文件。每次导出并发给客户时自动记一个版本（Rev.0、Rev.1…，只增不改），保存当时的结构快照；任意两版、或某版与当前结构可以对比，列出新增 / 修改 / 删除。第一次发给客户的就是 Rev.0（合同基线）。

### F3 设备

1. 设备按"条目 + 台数"记录，应交项和 MDL 统计都按条目，不按台。导入设备清单 Excel（200 多条）：设备编号、设备名、设备种类、供应商、台数、别名；其他列原样存为属性。再次导入时比对差异（有编号按编号对上，没编号按名称对上）。也可以在页面上从 Excel 粘贴多行，同样先预览再确认。
2. 设备编号选填：有编号的项目内唯一、不复用；没编号的（数量多、没位号的）用名称区分，没编号的名称不能重复，文件名里不带设备编号。界面按设备条目显示，展开可填每台出厂编号（选填，只有填了的台才有记录，几千台也不会建几千条）。
3. 增删改留历史（字段级前→后、操作人、原因），可恢复到某次修改前；没用过的设备可以删除、编号释放；用过的（应交项挂了文件、进过传送单或阶段基线，或最近一次发 MDL 给客户时已经存在）只能停用，编号不复用（2026-10-27 第 17F 步改）。
4. 设备改名时，已有文件的当前版本同步改名，历史版本保留原名。

### F4 存文件

1. 方式一：在应交矩阵或文件夹里点"上传到此处"，位置已知，直接显示命名预览后存入。
2. 方式二：一句话描述 + 拖入一个或多个文件；可先选供应商缩小范围。系统用规则（设备名、编号、别名、文件种类关键词、文件夹名）优先匹配"未到"的应交项，逐行显示结果、置信度和命名预览，可改；确认后存入并跳转。
3. 共用规则：同一应交项下标题相同、格式相同的文件已存在则自动升版（按设备的也一样，一台设备下可以有好几份不同的文件，2026-10-25 改）；内容完全相同的拦截；选择来源；识别不出的进待归类（保持原名）；上传无必填表单。
4. 版本保留：供应商和我方文件保留最新 3 版，更早的进回收区 90 天；客户文件全部保留；被基线引用的版本不清除。

### F5 命名与编号

| 文件类型 | 规则 | 例 |
| --- | --- | --- |
| 按设备 | 里程碑号.种类号.设备编号_种类名-设备名-YYYYMMDD-V版本 | 3.5.72_Cut sheet-Mixer A-20260226-V1.pdf |
| 多台设备 | 设备编号用 & 连接 | 3.5.72&73_Cut sheet-… |
| 按设备、一项有好几份文件 | 里程碑号.种类号.设备编号_种类名-设备名-文件标题-YYYYMMDD-V版本（2026-10-25 加） | 3.8.13_P&IDs-Tool A-Wiring diagram-20260302-V2.png |
| 按模块 | 同"不对应设备"：里程碑号.种类号_种类名-文件标题-YYYYMMDD-V版本；模块只作分类记录，不进文件名 | 3.3_General Arrangement Drawings-（文件标题）-20260226-V1.pdf |
| 不对应设备 | 里程碑号.种类号_种类名-文件标题-YYYYMMDD-V版本 | 3.12_Layout drawing-Cleanroom 1F-20260226-V1.pdf |
| 客户文件 | 保持原名，放在"里程碑 / 文件种类"文件夹 | — |
| 识别不出 | 保持原名，进待归类（默认不加前缀，可配置前缀如 x；2026-10-25 改） | 未知文件.pdf |

- 日期取文件更新日：文件名中的日期 → 文件最后修改时间 → 上传日。
- 名称按配置里的写法原样输出；去掉 Windows 非法字符；导出路径 ≤ 260 字符。
- 命名模板按项目配置。文件名是由结构数据生成的"视图"，设备或种类改名后自动重算。

### F6 浏览与检索

1. 三种视图：按里程碑 / 文件种类；按设备种类 / 设备；按模块。同一文件在各视图里都能找到，存储只有一份。
2. 筛选：里程碑、文件种类、模块、设备种类、设备、供应商、来源、状态、关键字（文件名 / 编号 / 原始名）。
3. 文件详情：版本历史、操作记录、下载、重新归类；PDF 和图片在线预览。

### F7 应交矩阵与 MDL

1. 矩阵：行是文件种类，列是设备或模块，格子显示 未到 / 已到（当前版本）/ 不适用；点格子即可上传或查看。
2. 状态：未提交 / 已提交 / 客户审核中 / 已批准 / 需修改重交 / 不适用，及责任方（我方 / 供应商 / 客户）。状态**由提交记录和客户回复推出**（见第 6 条），也可单个或批量手改；手改时没有客户回复依据的标"无凭证"。每次改状态都记录**真实发生的日期**（如客户批准那天）和依据，与系统里的操作时间分开记。文件传进平台只表示"文件已到"，不等于已提交给客户。
3. 逾期：过截止日未提交自动标红；客户超过审核期限未回复，标"客户超期未审"。
4. 汇总：按里程碑和模块的完成率（已批准 ÷ 应交，不含不适用）、各方待办数（按责任方，未指定的单独列）、逾期数。
5. 导出 MDL：**Excel 和 PDF** 两种（A4 横向），平台统一格式、参照业界常见 MDL（Document Register）样式，不照搬任何客户的表格；表头区有项目名称、客户名称、总包名称、MDL 文件编号、版本号、发出日期、编制 / 审核 / 批准签字栏和版本记录；主表按里程碑分组、状态用颜色和图例；按设备的种类只显示汇总并写明待交的模块和台数，另附逐台缺件明细；每页带"系统生成"标识（平台名、版本、生成时间、页码）；只含"列入客户 MDL"的文件种类，标出相对上一版的变化。Excel 版改过的状态、日期、备注可导回（只认平台导出的文件），导回前列差异确认。缺件清单可单独导出给供应商。
6. 提交与客户回复（混合方式：大部分自动、少量手动，手动录入的单位是一张传送单或一封回函，而不是一份文件）：
   - **提交记录**：在平台里勾选应交项生成传送单（Excel / PDF，带编号）时自动记录；第 15 步的交付包同样自动记录；在客户系统或邮件里已交的可事后批量补记。
   - **客户回复**：MDL 导回时自动生成；客户退回的带章文件投进平台时按规则识别结论、人确认（第 12 步）；按传送单一次录入整张单的结论；第二版 AI 识别审核章和意见单；第三版从 Procore 等系统自动拉取。
   - **审核代码**：客户审完给的结论标记（如 1 批准 / 2 带意见批准 / 3 修改重交 / 4 仅供参考，各客户叫法不同），按项目配置对应到平台状态，并标明"算不算完成""要不要重交"；与状态映射是同一类配置。
   - **客户审核期限**：项目设置里的天数；超期只提醒，"视为批准"必须手动标并写合同依据。
7. 闭环检查：里程碑可关闭的条件是每个应交项都已批准（带意见批准的需拿到最终批准）且有回复日期和依据、不适用的有依据、客户新增要求都已确认接受与否、批准后没有再传新版本（第 11 步有文件版本后生效）；内部要求未完成、文件种类没写要求依据只提示不挡关闭；关闭只记录日期、操作人、依据，不锁定，关闭后有变动会提示，可重新打开；有未闭环项时可写明原因强制关闭；可导出里程碑关闭清单（Excel / PDF，列出每项批准的版本、日期、凭证）。带意见批准在完成率里算"已批准"，在闭环检查里要求最终批准。

### F8 交付、镜像与基线

1. 交付包：zip，目录为 项目 / 设备种类 / 设备 / 文件（也可选按里程碑 / 文件种类）；可按全部、里程碑、种类、单台设备导出；附文件清单。
2. 共享盘只读镜像：最新版按交付目录结构同步到共享文件夹，同盘用硬链接不占空间。
3. 阶段基线：冻结时记录每个文件的当前版本和缺件情况；可查看、对比、按基线重新导出。

### F9 存量导入与清理

1. 指定本地或共享目录。（原写"可附索引 Excel"，第 14A 步决定不单独做：预演报告改好导回即可）
2. 去重（哈希）、版本归并（按原名中的 V / Rev 和日期排序）、识别（含文件夹名）、命名。
3. 预演报告 Excel：原路径、识别结果、新名、重复 / 旧版 / 疑似新设备；可改完导回执行。
4. 后台执行、显示进度、可暂停；失败逐条给原因；不改动原目录；整批可撤销。

### F10 账号、权限与审计

1. 本地账号登录；三档权限 + 项目成员。登录方式可插拔，第一版只实现本地账号，预留 AD / LDAP、单点登录（OIDC）；三档权限作为初始角色数据存在数据库里，以后可增加角色。
2. 所有写操作进变更记录，可按项目、对象、人、时间查询和导出。

## 8–9. 技术方案（已选定 A）

方案 A：Python 轻量单体——FastAPI 后端 + PostgreSQL + 一个后台工作进程（任务存在数据库任务表里，带租约，崩溃可续跑）；前端 Vue 3 + TypeScript；部署为两个 Windows 服务。

选 A 而不选 D（容器化）的原因：D 的好处要到多台服务器、有专人运维时才体现；在 8 GB 的 Surface Pro 7 上跑 WSL2 + Docker 会很吃力；D 里的 MinIO、Redis、Celery、独立搜索引擎第一版都用不上；A 以后可以平滑容器化——代码不变，只是把各部分装进容器。为此 A 从一开始就做到：配置全部走配置文件和环境变量；数据目录、文件目录路径可配置；不依赖 Windows 专有功能（硬链接镜像除外，换平台时改为复制或符号链接）。

## 10. 已确认事项

- 技术方案：A。
- 按模块分区的文件：不用模块名，按文件种类 + 文件标题命名。
- 不另外提供设备清单和文件样本；开发按 MDL 和本 PRD 的规则实现，调试时由用户指出问题。设备清单导入器按"列名可映射"设计，遇到未知格式让用户指定列，而不是报错。

## 11. 产品化要求（2026-10-23 确认）

**定位**：平台最终作为产品卖给其他总包企业。每家客户在自己内网单独部署一套（私有化部署、单租户）；不做云端在线版，不做多租户。第一版仍先在试点项目上跑通，但下面 8 条从第一版起就按产品标准实现，因为它们影响数据结构，晚改代价大。

| # | 要求 | 原因 | 第一版怎么做 |
| --- | --- | --- | --- |
| P1 | 项目结构在平台内设置，MDL 由平台输出 | 每家客户的 MDL 格式不同，且多为手工维护（合并单元格、汇总块、进度写在状态栏），通用解析不可靠 | 里程碑、文件种类、模块在平台内录入（编号自动建议、粘贴多行、批量、复制已有项目）；MDL 按平台统一格式导出；不做客户 MDL 自动导入；`mdl_templates` 表第一版不使用，预留给以后（如导出格式、第二版 AI 导入） |
| P2 | 状态文字、里程碑编号规则、命名模板按项目配置 | 每家客户叫法不同 | 状态映射表（原文字 → 平台状态 + 责任方，用于翻译旧 MDL 的状态文字）、命名模板、编号规则都存在数据库里；产品带一套通用默认规则 |
| P3 | 界面多语言 | 总包客户和 MDL 大多是英文 | 前端用 vue-i18n，组件里不直接写文字；默认中文，预留英文 |
| P4 | 登录方式可插拔 | 企业客户要求用域账号 / 单点登录 | 用户表有 auth_provider、external_id；登录走"认证提供方"接口，第一版只实现本地账号；角色存为数据 |
| P5 | 文件存储接口化 | 客户可能用 NAS 或对象存储 | 定义存储接口，第一版只实现本地磁盘 |
| P6 | 不依赖 Windows | 客户 IT 多要求 Linux 服务器 | 路径用 pathlib；硬链接失败改复制；Windows 服务注册只在部署脚本里；第 17 步同时提供 Windows 和 Linux / Docker 两种部署 |
| P7 | 升级与备份可靠 | 客户升级不能靠人工 | 启动或安装时自动执行数据库迁移；提供备份、恢复命令 |
| P8 | 测试样本脱敏 | 产品代码里不能带客户项目数据 | 仓库中只放虚构样本，代码和默认数据里不出现真实客户或公司名称；试点项目的真实 MDL 和 AI 导入的评测标准答案只放本机 `backend/tests/fixtures/private/`（不提交），缺失时相关测试跳过 |

**第一版不做（以后再加，不影响现有结构）**：授权码与用户数限制、计费、多租户、在线版、图形化安装向导。

**需要用户自行确认的非技术事项**

- 知识产权：若平台在工作时间、用公司资源或公司项目数据开发，成果可能归公司所有。对外销售前应与公司确认，或咨询律师。
- 第三方许可：目前选用的组件（FastAPI、Vue、Element Plus、PostgreSQL、openpyxl 等）都允许商用；第二版选用的 Qwen 模型需逐个核对许可。代码仓库公开，采用 Apache 2.0 许可证（2026-10-27 决定，原定保持私有）。

## 开发顺序

1. 数据模型 + 项目结构设置 + 生成应交项 + MDL 导出 + 设备清单导入：用试点项目的结构验证。
